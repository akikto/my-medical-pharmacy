Implement PHASE 3 for the MY MEDICAL pharmacy desktop app.

IMPORTANT PROJECT RULES
- This is the existing native Tauri + SQLite offline pharmacy application.
- Preserve all existing functionality.
- DO NOT modify or redesign the Home dashboard.
- Do not break or redesign completed Phase 1 or Phase 2 functionality.
- Keep the existing green workspace visual system and shared UI patterns.
- Use INR (₹) where currency is displayed.
- All data operations must remain offline/local SQLite.
- All financial/stock-changing operations must be transactional and auditable.
- Do not introduce arbitrary SQL execution from the renderer.
- Reuse the existing typed Tauri/native data-access architecture.
- Do not create a second backup system. Reuse the existing photo-inclusive ZIP backup/restore system.
- Do NOT commit, push, publish, or create a release.
- Do NOT run broad cargo fmt changes. Only format files directly touched if necessary.

PHASE 3 GOAL
Build a complete Purchase + Supplier financial workflow:

3A. Purchase Invoice Management
3B. Purchase Return
3C. Supplier Payment
3D. Supplier Ledger
3E. Purchase GST
3F. Purchase Invoice Attachments
3G. Full regression + visual QA

Work in small, safe steps. After each sub-phase, run focused tests before moving to the next one.

--------------------------------------------------
3A — PURCHASE INVOICE MANAGEMENT
--------------------------------------------------

First inspect the existing purchase schema, services, UI and existing purchase-entry workflow.

Do NOT replace working purchase functionality unnecessarily.

Implement:

1. Purchase history/list:
   - Invoice number
   - Supplier
   - Purchase date
   - Total amount
   - GST/tax amount where applicable
   - Payment status
   - Outstanding supplier balance where applicable

2. Open/view saved purchase invoice.

3. Edit saved purchase invoice:
   - Allow editing appropriate purchase header and line-item information.
   - Correctly reverse the original stock effect before applying the edited purchase.
   - Recalculate stock from the new purchase lines.
   - Preserve historical integrity.
   - Do not silently modify unrelated sales or other purchases.
   - All changes transactional.

4. Delete/cancel purchase:
   - Do NOT physically destroy historical financial information if the existing architecture supports cancellation/void.
   - Prefer an auditable cancelled/void state.
   - Reverse stock safely when cancelling.
   - Prevent double reversal.
   - Clearly show cancelled state.
   - Existing sale history must remain unchanged.

5. Validation:
   - Invalid medicine/batch IDs rejected.
   - Quantity must be > 0.
   - Purchase price cannot be invalid/negative.
   - Required supplier/invoice information validated.
   - Duplicate invoice handling must be explicit and safe.
   - Cannot edit/cancel an already-cancelled purchase incorrectly.

6. Existing purchase history must remain compatible.

Tests:
- create purchase
- edit purchase
- stock before/after edit
- cancel purchase
- stock after cancellation
- invalid quantity
- invalid price
- duplicate invoice
- repeated cancellation protection
- transaction rollback on failure

--------------------------------------------------
3B — PURCHASE RETURN
--------------------------------------------------

Implement supplier purchase returns.

Requirements:

1. Return from an existing purchase invoice.

2. Return must be batch-aware.

3. Show:
   - Original purchase quantity
   - Already returned quantity
   - Available quantity to return
   - Purchase price
   - Return quantity
   - Return value

4. Never allow return quantity greater than available purchased quantity.

5. On successful return:
   - Reduce current stock safely.
   - Record return transaction.
   - Reduce the amount owed to the supplier appropriately.
   - Preserve the original purchase invoice.
   - Create an auditable purchase-return record.

6. Do not allow returning stock that has already been returned.

7. Handle edge cases:
   - Partial return
   - Full return
   - Multiple partial returns
   - Already cancelled purchase
   - Missing batch
   - Insufficient current stock

IMPORTANT:
If returned stock has already been sold, do NOT blindly make stock negative.
Use the existing stock/business rules and reject the return when the current stock cannot safely support it, with a clear message.

Tests:
- partial return
- full return
- multiple partial returns
- over-return rejection
- already-returned quantity protection
- insufficient stock rejection
- supplier balance adjustment
- rollback on failure

3C — SUPPLIER PAYMENT
--------------------------------------------------

Implement supplier payment entry.

Supplier payment fields:

- Supplier
- Payment date
- Amount
- Payment method
- Reference/transaction ID
- Notes

Payment methods can include the existing appropriate modes such as:
- Cash
- Bank
- UPI
- Other

Requirements:

1. Supplier payment reduces outstanding supplier balance.

2. Partial payment supported.

3. Full payment supported.

4. Payment cannot create an invalid negative supplier balance.

5. If payment exceeds outstanding balance:
   - reject by default
   - do not silently create negative balance

6. Payment must have an auditable transaction record.

7. Payment can be viewed later.

8. If UPI/reference is used, store the reference exactly as entered.

9. Do not claim that a UPI payment is externally verified unless the existing application has actual verification.

Tests:
- partial payment
- full payment
- overpayment rejection
- invalid amount
- payment history
- supplier balance before/after
- rollback on failure

3F — PURCHASE INVOICE ATTACHMENTS
--------------------------------------------------

Add optional purchase invoice attachment support.

Supported practical types may include:
- PDF
- JPG/JPEG
- PNG

Requirements:

1. Attach file to a purchase invoice.

2. View/open attachment using the existing safe local file/opening mechanism.

3. Store metadata/reference safely.

4. Do NOT store large binary files directly inside SQLite unless the existing architecture specifically requires it.

5. Integrate attachments into the EXISTING photo-inclusive ZIP backup/restore system.

6. Backup must include referenced purchase attachments.

7. Restore must validate:
   - file presence
   - file size
   - SHA-256 checksum
   - database reference

8. Restore must remain atomic/safe:
   - if an attachment is missing/corrupt, do not partially install the restore.
   - rollback database and attachment files as needed.

9. Legacy `.db` backup compatibility must remain intact.

10. Existing medicine photo backup behavior must NOT regress.

Tests:
- purchase with no attachment
- PDF attachment
- image attachment
- multiple purchase attachments
- odd filename
- missing attachment
- corrupted attachment
- backup/restore round trip
- mixed medicine photos + purchase attachments
- legacy DB backup compatibility
- orphan attachment handling

IMPORTANT:
Reuse the existing backup manifest/checksum architecture rather than creating another backup format.
