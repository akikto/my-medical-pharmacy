==================================================
4A — SALES RETURN / REFUND
==================================================

First inspect the existing sales invoice, sale-item, batch allocation,
stock, customer ledger and payment architecture.

Implement a proper sales-return workflow.

ENTRY:
- Start from an existing completed sales invoice.
- Show invoice number/date/customer/payment mode.
- Show every sold medicine/item.
- Show original quantity.
- Show already-returned quantity.
- Show remaining returnable quantity.
- Show sale price.
- Show applicable GST/tax snapshot.
- Allow partial or full return.

VALIDATION:
- Return quantity must be > 0.
- Return quantity cannot exceed the remaining returnable quantity.
- Cannot return from a cancelled/void invoice.
- Cannot return an item that was never sold.
- Invalid medicine/batch references must be rejected.
- Prevent duplicate/double return.

STOCK:
- Return must be batch-aware.
- Returned quantity must go back to the correct original batch where the
  existing architecture permits.
- Do not blindly create stock in a different batch.
- Preserve batch/expiry information.
- Stock changes must be transactional.

IMPORTANT STOCK SAFETY:
If the original sold batch can no longer safely accept the returned quantity
because of current stock state or other business constraints, do not silently
move the quantity to another batch.

Use the existing stock rules and reject unsafe returns with a clear message.

REFUND:
Support:
- Cash refund
- UPI refund/reference where appropriate
- Other existing payment modes where appropriate
- Credit-sale return / due reduction

Do not claim that a UPI refund is externally verified.

For a credit sale:
- Returned amount must correctly reduce the customer's outstanding due.
- Do not create a negative customer balance.

For a paid sale:
- Record the refund transaction clearly.

GST:
- Use the original sale-time GST snapshot.
- Do not recalculate an old invoice using today's GST settings.
- Return tax amounts must be derived from the original transaction snapshot.

RETURN RECORD:
Create an auditable sales-return record containing:
- return ID/reference
- original invoice
- date/time
- customer
- item/batch
- quantity
- amount
- tax/refund information
- payment/refund method
- notes
- status

Tests:
- partial return
- full return
- multiple partial returns
- over-return rejection
- duplicate return protection
- cancelled invoice return rejection
- stock restoration
- GST snapshot correctness
- credit-sale due adjustment
- paid-sale refund
- transaction rollback

==================================================
4B — INVOICE VOID / CANCEL
==================================================

Implement safe invoice cancellation/void.

Requirements:

1. Existing completed invoice can be cancelled according to business rules.

2. Cancellation must:
   - reverse its stock effect safely
   - reverse the related customer due effect when applicable
   - reverse/adjust the financial ledger correctly
   - preserve the original invoice as historical/auditable data
   - mark it clearly as Cancelled/Void

3. Never physically destroy the historical invoice just to cancel it.

4. Cannot cancel an already-cancelled invoice.

5. Cannot accidentally cancel a different invoice.

6. All changes must happen in one transaction.

7. Historical GST snapshot must remain stored.

8. If cancellation cannot safely reverse stock/ledger state:
   - reject the cancellation
   - make no partial changes
   - explain the reason

IMPORTANT:
Do not simply delete sale rows.

Tests:
- normal invoice cancellation
- stock reversal
- customer due reversal
- paid invoice cancellation
- credit invoice cancellation
- repeated cancellation protection
- rollback on failure
- historical invoice remains visible as Cancelled

==================================================
4C — SAFE INVOICE EDIT
==================================================

Implement safe editing of a completed invoice only where business rules permit.

DO NOT create a dangerous "rewrite history" system.

The preferred architecture is:

Original invoice remains auditable.

An edit creates a controlled revision/correction, or safely reverses the
original transaction and applies the corrected transaction inside one
transaction, while preserving the original information.

Support appropriate editable fields such as:
- customer
- item quantity
- item sale price
- payment mode
- payment/reference information
- notes

Do NOT allow unsafe changes to historical batch allocation.

For quantity changes:
- correctly adjust stock
- validate available stock
- preserve FEFO/batch rules where applicable

For price changes:
- store corrected sale-time price/tax snapshot
- do not modify medicine master pricing

For customer changes:
- correctly reverse old customer's due impact
- correctly apply new customer's due impact
- prevent negative/incorrect balances

For payment-mode changes:
- correctly update payment/credit accounting
- preserve audit trail

GST:
- Existing invoice's original GST snapshot must remain auditable.
- Corrected transaction must use the appropriate saved/configured GST rule
  without changing unrelated historical invoices.

Tests:
- edit customer
- edit quantity
- edit sale price
- edit payment mode
- edit credit sale
- edit paid sale
- insufficient stock rejection
- customer due recalculation
- GST recalculation/snapshot
- rollback on failure
