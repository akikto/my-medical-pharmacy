SUB-PHASE 2A — MEDICINE MASTER DATA MODEL
==================================================

First inspect the existing medicine, batch, inventory, purchase, sale, POS and migration schema.

Do not duplicate fields that already exist.

Add only missing medicine-master fields needed for Phase 2.

Medicine should support, where appropriate:

- barcode
- product type
- composition
- uses
- adult dose
- child dose
- photo/image reference
- medicine-level GST rate, if not already available from Phase 1
- existing name/company/manufacturer fields where already supported
- existing strength/unit/pack fields where already supported

Product Type must be configurable/extensible rather than hard-coded to only three values.

Initial commonly used values may include:
- Tablet
- Capsule
- Syrup
- Suspension
- Injection
- Cream
- Ointment
- Drops
- Inhaler
- Powder
- Other

Do not assume these are the only possible values.

BARCODE RULES
-------------
- Barcode must be optional.
- Do not require a barcode for every medicine.
- Barcode values should be normalized consistently.
- Prevent duplicate barcode values across active medicine records.
- If the database supports unique constraints safely, use them.
- Otherwise enforce uniqueness transactionally.
- Do not silently replace an existing barcode.

PHOTO RULES
-----------
- Medicine photo must be optional.
- Do not store unnecessarily large raw images in SQLite.
- Reuse the existing image/file storage approach if one exists.
- If no suitable approach exists, use a local app-managed image reference with safe validation.
- Preserve offline operation.
- Do not introduce cloud storage.

GST
---
- Do NOT introduce a new fixed GST rate.
- Reuse the Phase 1 medicine-level GST model.
- Existing GST precedence must remain:
  POS override → medicine rate → pharmacy default.

MIGRATION
---------
Create a safe migration only if required.

Requirements:
- Existing medicines remain valid.
- Existing batches remain linked.
- Existing sales remain unchanged.
- Existing purchases remain unchanged.
- Existing historical GST snapshots remain unchanged.
- Migration must be idempotent/safe on startup.
- No destructive migration.

TESTS
-----
Add isolated tests for:
- migration
- existing data preservation
- barcode uniqueness
- optional barcode
- product type
- optional photo
- medicine-level metadata
- GST compatibility

Run:
- renderer tests
- Rust tests
- typecheck
- build
- git diff --check

STOP and report results before moving to the next sub-phase if a migration/data-integrity problem is found.

SUB-PHASE 2E — BULK STOCK UPDATE + MULTI-SELECT

Add safe bulk stock management to Inventory.

Requirements:
- Multi-select mode.
- Select individual medicines.
- Select all visible filtered medicines.
- Clear selection.

Confirmation:
- show a clear confirmation before applying a bulk operation
- display number of affected records

SUB-PHASE 2H — STOCK-OUT ORDERING + PURCHASE QUANTITY SUGGESTION
==================================================

Integrate stock alerts with ordering workflow without creating a duplicate purchasing system.

When stock reaches zero/low stock:
- provide an Order action where appropriate
- preselect the medicine
- allow supplier selection
- allow requested quantity
- allow notes

Do not automatically create a purchase invoice merely by pressing Order.

Prefer creating/using the existing Home Order List / purchase-order preparation functionality if already available.

PURCHASE QUANTITY SUGGESTION
----------------------------
Provide a suggested purchase quantity based on available local data.

Possible calculation inputs:
- recent sales/usage
- current stock
- reorder level
- configurable target stock level
- existing pending order quantity if supported

Do NOT pretend to have accurate forecasting when insufficient data exists.

If there is insufficient sales history:
- show that the suggestion is based on limited data
- allow manual quantity override

The suggestion must NEVER automatically place an order.

Example concept:

Suggested Quantity =
Target Stock - Current Sellable Stock - Pending Order Quantity

If target stock is derived from usage:
- document the calculation clearly
- keep it deterministic and testable

Expired stock must not be treated as sellable stock.

TESTS
-----
- zero stock
- low stock
- sufficient stock
- insufficient sales history
- recent usage
- expired stock
- pending order if supported
- manual override
- Order action does not create an invoice automatically
