ISSUE 1 — NATIVE FEFO ENFORCEMENT

Fix the native checkout layer so FEFO is enforced independently of the renderer.

Requirements:
- Native checkout must determine eligible batches from trusted database state.
- Expired batches must never be eligible for normal sale.
- When multiple eligible batches exist, allocation must follow earliest-expiry-first.
- Renderer-supplied batch allocations must NOT be blindly trusted.
- Quantity validation must remain intact.
- Prevent selling more than available eligible stock.
- Preserve the existing normal POS behavior and UI.
- Do not change the existing FEFO user experience unnecessarily.

Add focused Rust tests for:
1. single valid batch
2. multiple valid batches with different expiry dates
3. expired batch + valid batch
4. requested quantity spanning multiple batches
5. insufficient eligible stock
6. renderer attempts to select a later-expiry batch while an earlier eligible batch exists

The native layer should reject or normalize invalid allocation requests according to the existing application architecture, but it must never allow a sale that violates FEFO.

ISSUE 2 — REMOVE/RESTRICT ARBITRARY RENDERER SQL

Review `execute_sql_transaction` and all renderer call sites.

Goal:
- Production renderer code must not be able to submit arbitrary SQL to the native layer.
- Replace renderer-facing arbitrary SQL calls with narrow, typed application commands/services wherever they are used.
- Keep database transaction capability internally where required.
- Preserve existing functionality.

Requirements:
- Identify every current caller of `execute_sql_transaction`.
- For each caller, replace arbitrary SQL with the appropriate typed native command/service.
- If a SQL command is required only for development/demo/testing, guard it strictly behind development-only code and ensure it cannot be reached from a production build.
- Do not break migrations, backup/restore, internal database initialization, or native Rust code that legitimately requires SQL.
- Do not introduce an artificial security claim; report exactly what was removed/restricted.

Add tests/source checks proving that production renderer code cannot invoke arbitrary SQL.

ISSUE 3 — AUTOMATIC BACKUP RETENTION

Implement a conservative retention policy for AUTOMATIC close-time backups.

Requirements:
- Keep recent automatic backups according to a clearly documented retention count.
- Remove only older automatic backups.
- Never delete manually created/user-selected backups through automatic cleanup.
- Never delete the currently active database.
- If cleanup fails, the app should still be able to close normally.
- Do not allow backup cleanup to interfere with backup creation.
- Handle missing backup directories safely.
- Keep behavior deterministic and easy to explain.

Use a constant for the retention count rather than hard-coding it in multiple places.

Add tests for:
1. fewer backups than retention limit
2. exactly retention limit
3. more than retention limit
4. manual backup files are preserved
5. cleanup failure does not prevent normal app shutdown
